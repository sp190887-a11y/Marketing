# АМ Клуб — технические требования, вытекающие из юридической модели

Версия 1.0 от 15.09.2026

## 1. Один продукт на телефоне и компьютере

`/club` — единое клиентское веб-приложение/PWA. Один аккаунт, одна серверная БД, одни документы и согласия. PWA отличается только способом установки и адаптацией интерфейса.

`/club/admin` — отдельный административный контур. Клиентский frontend не содержит переключателя и административной бизнес-логики.

## 2. Registration API

До отправки телефона должны быть подтверждены три независимых пункта:

1. `age_18_confirmed = true`
2. `rules_version = 1.0-2026-09-15` и `rules_accepted = true`
3. `pd_consent_version = 1.0-2026-09-15` и `pd_consent = true`

`marketing_consent` — отдельный необязательный boolean, по умолчанию `false`.

Backend не должен доверять только клиентскому JS: обязательные поля проверяются сервером.

## 3. Consent ledger

Таблица/журнал должен быть append-only:

```text
id
customer_id nullable
registration_attempt_id
consent_type: age | rules | personal_data | marketing | channel_*
document_version
action: accept | revoke
occurred_at_utc
ip
user_agent
session_id/request_id
source: web | pwa | admin-assisted
text_hash_or_document_id
```

Нельзя перезаписывать `accepted=true` на `false`. Отзыв — новая запись.

## 4. Document versioning

Каждый пользовательский документ имеет immutable version ID. URL может указывать на актуальную версию, но сервер обязан уметь доказать, какой текст был принят конкретным пользователем. При публикации новой существенной версии старый файл/хэш должен сохраняться в архиве.

## 5. Marketing suppression

Перед каждой рекламной отправкой сервер повторно проверяет последнее состояние `marketing` по пользователю и каналу. Нельзя формировать список рассылки раз в неделю и отправлять без повторной проверки отзыва.

Сервисные сообщения идут отдельным message_type и не должны маскировать рекламу.

## 6. Data location

`DATABASE_URL` production указывает на PostgreSQL на территории РФ. Нельзя использовать текущий зарубежный staging Neon как production-хранилище российских персональных данных.

Backup production-БД также размещается в соответствии с требованиями локализации и внутренней моделью защиты.

## 7. PIN и сессии

- PIN только hash (предпочтительно Argon2id с индивидуальной солью);
- 4-значный PIN требует rate limiting и lockout/backoff;
- первичное подтверждение телефона — одноразовый код с коротким TTL;
- серверная сессия отзываема;
- cookie: Secure, HttpOnly, SameSite; срок контролируется сервером;
- список активных устройств/сессий должен позволять завершить чужую сессию;
- забытый PIN восстанавливается только после подтверждения через связанный канал/SMS.

## 8. Admin

- отдельная таблица/identity provider администраторов;
- роль `client` никогда не имеет admin permissions;
- middleware/server guard на каждом административном endpoint;
- 2FA для production admin;
- audit log для поиска клиента, просмотра карточки, ручного +АМ/-АМ, изменения акции/каталога, выгрузки данных, изменения согласий по обращению.

## 9. Immutable AM ledger

Баланс — производная ledger, а не редактируемое число. Любая отмена: отдельная отрицательная/положительная операция с ссылкой на исходную.

Возврат заказа, отписка, снятие реакции могут увести баланс ниже нуля. Backend не должен обрезать отрицательное значение до 0.

## 10. Subject rights API

Нужны server endpoints/admin workflow:

- экспорт данных пользователя;
- исправление профильных данных;
- отзыв marketing consent;
- закрытие участия;
- создание deletion/anonymization task;
- ручная проверка спорной операции;
- журнал статуса запроса и SLA.

## 11. Privacy by design

Не отдавать административному frontend полный набор полей в списках. Поиск клиента — по запросу; чувствительные подробности подгружаются только при открытии карточки уполномоченным администратором.

Логи приложений не должны содержать PIN, OTP, bot tokens, DATABASE_URL, session cookie или полные payload внешних платформ без необходимости.

## 12. Social adapters

Каждый адаптер Telegram/VK/MAX реализует общий контракт и передаёт Reward Engine нормализованное событие. Социальный адаптер сам не изменяет баланс.

Событие содержит идемпотентный `source_event_id`. Повторная доставка не создаёт повторную операцию.

## 13. Production acceptance

Юридический production acceptance считается PASS только если:

- данные, зарегистрированные на телефоне, видны с компьютера из общей БД;
- consent ledger отражает реальную последовательность accept/revoke;
- client не может вызвать admin endpoint;
- marketing=false реально исключает клиента из рассылки;
- backup восстановлен в тестовом окружении;
- выбранный production hosting подтверждён как российский;
- актуализировано уведомление Роскомнадзора;
- Telegram не включён в production до завершения cross-border checklist.
