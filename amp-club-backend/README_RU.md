# АМ Клуб — серверное ядро

## Что это

Python/Flask API + PostgreSQL для АМ Клуба. Клиентское PWA и desktop-браузер используют один API и одну БД. Админка использует тот же API, но отдельные admin-сессии и роли.

## Главное

- регистрация и PIN больше не хранятся в HTML/localStorage;
- PIN хранится только как PBKDF2-хэш;
- одноразовые коды хранятся как HMAC-хэш и имеют срок жизни;
- согласия пользователя пишутся в immutable `consent_ledger`;
- АМы меняются только вставкой в immutable `am_ledger`;
- прямой `UPDATE customers.balance_am` запрещён триггером;
- повтор операции по тому же `idempotency_key` не начисляет АМы второй раз;
- клиентские и административные сессии разделены;
- ручное создание заказов API не поддерживает: источник заказов — будущий CRM-коннектор.

## Миграции

Применяются по порядку:

```bash
psql "$DATABASE_URL" -f migrations/0001_base.sql
psql "$DATABASE_URL" -f migrations/0002_server_core.sql
```

`0001_base.sql` нужен для новой чистой PostgreSQL. На существующей тестовой БД АМ Клуба достаточно применить `0002_server_core.sql` после проверки на временной ветке БД.

## Переменные окружения

Обязательные перед production:

```text
DATABASE_URL=postgresql://...
OTP_PEPPER=<случайная длинная секретная строка>
ADMIN_BOOTSTRAP_TOKEN=<одноразовый длинный секрет>
ALLOWED_ORIGINS=https://club.amplituda-nn.ru
SMS_MODE=test
```

Дополнительно:

```text
OTP_TTL_MINUTES=5
OTP_RESEND_SECONDS=60
CLIENT_SESSION_DAYS=90
ADMIN_SESSION_HOURS=12
```

### Важно про SMS

Пока `SMS_MODE=test`:

- регистрация: код `1111`;
- восстановление PIN: код `2222`.

До выбора и проверки финального российского SMS-провайдера режим production не включать. SMS Holding пока считается кандидатом, но формат его API в коде намеренно не выдуман.

## Первый администратор

Администратор не встроен в клиентское приложение.

Первый owner создаётся один раз:

```http
POST /api/admin/bootstrap
X-Bootstrap-Token: <ADMIN_BOOTSTRAP_TOKEN>
Content-Type: application/json

{
  "login": "owner",
  "password": "длинный-пароль-не-менее-10-символов",
  "display_name": "Владелец"
}
```

После появления первого `admin_users` bootstrap автоматически перестаёт работать (`409 already_bootstrapped`). На production после создания владельца `ADMIN_BOOTSTRAP_TOKEN` нужно убрать из окружения.

## Клиентская регистрация

1. `GET /api/legal/current` — клиент получает текущие версии документов.
2. `POST /api/client/register/start` — телефон + три обязательных подтверждения (`18+`, Правила, ПД) + необязательная реклама.
3. Сервер создаёт одноразовый код и сохраняет юридическое доказательство, которое будет связано с регистрацией.
4. `POST /api/client/register/verify` — код + PIN + профиль.
5. Создаётся клиент, серверная сессия и immutable записи согласий.

## Вход

```http
POST /api/client/login
{
  "phone": "9991234567",
  "pin": "1234"
}
```

После 5 последовательных неверных PIN вход блокируется на 15 минут.

## Восстановление PIN

- `POST /api/client/recovery/start`
- `POST /api/client/recovery/verify`

После успешного восстановления все старые клиентские сессии отзываются.

В дальнейшем каналы восстановления: Telegram -> MAX -> резервная SMS.

## Согласия

- `GET /api/client/consents`
- `POST /api/client/consents/marketing`

Рекламное согласие не является условием участия в АМ Клубе.

## АМы

Администратор делает ручную корректировку только с причиной:

```http
POST /api/admin/customers/<customer_uuid>/adjust-am
Authorization: Bearer <admin-token>

{
  "amount": 100,
  "reason": "Компенсация клиенту",
  "idempotency_key": "support-ticket-12345"
}
```

Повтор с тем же `idempotency_key` возвращает существующую операцию и не меняет баланс второй раз.

## Поиск клиента администратором

```http
GET /api/admin/customers?q=89991234567
```

Без `q` API возвращает пустой список. Это специально: админка не выгружает всю клиентскую базу при простом открытии страницы.

## Поддержка

```http
POST /api/client/support
Authorization: Bearer <client-token>
```

Обращение пишется в общую БД. Почтовое уведомление на `2820580@mail.ru` подключается отдельным серверным адаптером, не через `mailto:`.

## Тесты

GitHub Actions поднимает отдельный PostgreSQL 16 и проверяет:

- юридические документы;
- обязательность отдельных согласий;
- регистрацию;
- вход с другого устройства;
- поиск зарегистрированного клиента администратором;
- отзыв/возврат рекламного согласия;
- immutable AM ledger;
- запрет прямого редактирования баланса;
- идемпотентность ручной операции;
- восстановление PIN и отзыв старой сессии;
- серверный тикет поддержки.

Локально:

```bash
pip install -r requirements.txt
PYTHONPATH=. pytest -q
```

## Что обязательно заменить перед боевым запуском

1. PostgreSQL должен быть размещён в РФ.
2. Выбрать финального российского хостинг-провайдера/ЦОД.
3. Подключить реальный SMS-провайдер.
4. Настроить `club.amplituda-nn.ru` и HTTPS.
5. Создать `privacy@amplituda-nn.ru`.
6. Включить админскую 2FA до production.
7. Подключить CRM-коннектор для заказов и автоматического начисления.
8. Настроить резервное копирование и тест восстановления.
